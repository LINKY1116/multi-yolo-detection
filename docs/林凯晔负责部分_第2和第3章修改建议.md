## 2. 第 2 章：项目立项怎么改

第 2 章主要回答三个问题：这个项目为什么可行、项目准备完成什么目标、项目范围包括哪些内容。

### 2.1 可行性研究

#### 2.1.1 资金可行性分析

可以重点写“成本较低、资源可复用、开源工具为主”。

建议表达：

本项目开发所需资金投入较低。系统主要基于开源 YOLO 框架、Flask 后端框架、Vue 前端框架、MySQL 数据库以及 OpenCV 等成熟工具进行开发，不需要购买大型商业软件。项目训练与演示可使用现有计算机设备完成，数据集可优先采用公开数据集或小组自行整理的数据集。AI 问答部分可通过 DeepSeek API 等大模型接口实现，也可以保留本地兜底分析逻辑，避免系统核心功能完全依赖外部付费服务。因此，从资金投入角度看，本项目具有较高可行性。

#### 2.1.2 技术可行性分析

可以重点写“技术栈成熟、模块划分清晰、实现路径可行”。

建议表达：

本项目采用 YOLOv8、Flask、Vue、Element Plus、OpenCV 和 MySQL 等成熟技术完成多用途目标检测系统设计。YOLOv8 适合进行目标检测任务，Flask 可以提供后端接口，Vue 和 Element Plus 可以构建可视化前端页面，OpenCV 可用于图片和视频处理，MySQL 可保存用户信息和检测历史。因此，项目涉及的主要技术均较成熟，具备技术可行性。

#### 2.1.3 操作可行性分析

可以重点写“用户不需要懂代码，前端流程清晰，适合课堂演示”。

建议表达：

本系统面向普通用户提供图形化操作界面。用户登录后，只需要选择检测场景或模型，上传图片、视频，或者打开摄像头，即可获得检测结果。系统会自动展示检测框、类别、置信度、检测统计和 AI 分析结果。不同模型对应不同 AI 回答角色，用户可以直接围绕检测结果提问，不需要了解模型训练或后端代码细节。系统操作流程清晰，学习成本较低，适合课程作业展示和后续扩展。

### 2.2 项目任务书

#### 2.2.1 项目具体目标

可以写成条目式目标：

1. 完成多用途 YOLO 目标检测系统的总体设计和功能规划。
2. 支持病虫害检测、花卉检测、火灾检测和无人机检测等多种应用场景。
3. 实现不同 YOLO 模型的管理、加载和切换，使系统能够根据场景执行检测任务。
4. 支持图片检测、视频检测和摄像头实时检测，并展示检测类别、置信度和结果文件。
5. 保存用户检测历史，支持历史记录查看、详情查看、下载和删除。
6. 接入 AI 智能分析与问答能力，使系统可以根据不同模型场景生成不同角色的回答。
7. 对前端界面进行美化，提升系统的可用性、展示效果和课堂答辩观感。

#### 2.2.2 项目范围

项目范围可以按模块写：

- 用户模块：用户注册、登录、退出和状态保持。
- 模型管理模块：模型上传、模型列表、模型加载、模型删除、当前模型展示。
- 多场景检测模块：病虫害检测、花卉检测、火灾检测和无人机检测等。
- 图片检测模块：图片上传、目标识别、结果图生成和检测统计。
- 视频检测模块：视频上传、抽帧检测、结果视频生成和视频分析。
- 摄像头检测模块：浏览器摄像头实时采集、后端检测和前端检测框显示。
- 历史记录模块：检测记录保存、查看、下载、删除和批量管理。
- AI 分析模块：检测报告生成、智能问答、不同模型角色提示词、本地兜底分析。
- 前端展示模块：仪表盘、检测页面、模型中心、历史记录页面和 AI 分析面板。

#### 2.2.3 生命周期模型选择

建议选择“增量模型”或“敏捷开发方法”。本项目功能模块较多，适合写增量模型。

建议表达：

本项目采用增量模型进行开发。多用途 YOLO 目标检测系统包含模型管理、图片检测、视频检测、摄像头检测、历史记录、AI 智能分析和前端展示等多个功能模块，若一次性完成全部功能，开发难度和测试压力都较大。因此，本项目适合按照功能优先级进行分阶段开发，在每个阶段完成一部分可运行、可验证的系统功能。第一阶段主要完成系统需求分析、总体架构设计和基础页面原型设计；第二阶段实现图片检测、视频检测和摄像头检测等基础检测功能；第三阶段增加多模型管理和模型切换能力，并训练或接入病虫害、花卉、火灾、无人机等不同场景的 YOLO 模型；第四阶段完善不同模型下的 AI 问答角色；第五阶段进行前端界面美化和系统测试。

## 3. 第 3 章：需求分析怎么改

第 3 章主要写系统需要实现什么功能，以及系统在界面、响应速度、安全性、可靠性等方面需要达到什么要求。

### 3.1 功能需求

建议先总述系统角色和总体功能：

本系统主要面向普通用户和系统管理员。普通用户可以选择检测模型、上传图片或视频、使用摄像头检测、查看检测结果、生成 AI 分析报告并进行智能问答；系统管理员可以管理模型文件、维护可用检测场景、查看系统检测记录并进行基础管理。

然后按模块展开：

#### 3.1.1 用户模块

- 用户可以注册账号并登录系统。
- 系统能够保存用户登录状态。
- 用户登录后才能使用检测和历史记录功能。

#### 3.1.2 模型管理模块

- 系统展示当前可用的 YOLO 模型列表。
- 用户或管理员可以根据场景选择病虫害、花卉、火灾、无人机等模型。
- 系统显示当前加载模型的名称、适用场景和类别信息。
- 管理员可以上传、加载或删除模型文件。

#### 3.1.3 目标检测模块

- 图片检测：用户上传图片后，系统返回目标框、类别、置信度和结果图。
- 视频检测：用户上传视频后，系统生成带检测框的视频结果，并统计主要检测信息。
- 摄像头检测：用户打开摄像头后，系统对实时画面进行检测并在前端叠加检测框。

#### 3.1.4 检测结果展示模块

- 系统展示检测到的目标数量、类别分布、最高置信度和平均置信度。
- 系统展示检测结果图片或视频。
- 当检测结果为空或置信度较低时，系统给出人工复核提示。

#### 3.1.5 历史记录模块

- 系统保存图片和视频检测记录。
- 用户可以查看检测时间、检测类型、使用模型、检测结果和置信度。
- 用户可以查看详情、下载结果文件、删除单条记录或批量删除记录。

#### 3.1.6 AI 智能分析与问答模块

- 系统根据检测结果生成自然语言分析报告。
- 系统根据当前模型类型切换 AI 回答角色。
- 病虫害模型对应农业植保助手。
- 花卉模型对应花卉识别助手。
- 火灾模型对应安全预警助手。
- 无人机模型对应低空安全监测助手。
- 当大模型接口不可用时，系统提供本地兜底分析结果。

### 3.2 非功能需求

#### 3.2.1 界面需求

系统界面应美观、清晰、易操作。前端页面需要突出模型选择、文件上传、检测结果展示和 AI 分析入口。检测页面应支持图片、视频和摄像头三种方式切换；模型中心应清楚展示不同场景模型；历史记录页面应便于用户查看和管理检测结果。整体风格应具有一定科技感，适合课堂展示。

#### 3.2.2 响应时间需求

图片检测应在较短时间内返回结果，保证用户能快速查看检测图和分析信息。视频检测由于处理帧数较多，可以允许较长等待时间，但系统应提供明确的处理状态提示。摄像头检测应尽量保持画面流畅，避免明显卡顿。AI 问答应在合理时间内返回结果，如果接口超时或失败，应提示用户并返回基础分析。

#### 3.2.3 可靠性需求

系统应能稳定处理常见图片和视频文件。当用户上传不支持的文件类型、模型加载失败、检测结果为空或 AI 接口调用失败时，系统不能崩溃，应给出清晰提示。检测结果和历史记录应正确保存，用户刷新页面后仍能查看历史数据。

#### 3.2.4 系统安全性需求

系统应通过登录机制区分用户身份，用户只能查看和管理自己的检测历史。上传文件需要限制类型和大小，避免异常文件影响系统运行。AI API Key 不应写死在代码中，可采用页面临时输入或环境变量配置方式。系统应避免向前端暴露敏感后端路径和密钥信息。

#### 3.2.5 可扩展性需求

系统应支持后续继续添加新的 YOLO 模型和检测场景。模型信息、适用场景、类别说明和 AI 角色提示词应尽量配置化，避免每增加一个模型都大幅修改系统代码。这样可以使项目从当前的病虫害、花卉、火灾、无人机检测继续扩展到更多目标检测任务。
